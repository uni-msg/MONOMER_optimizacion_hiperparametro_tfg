Conceptual

1. Introducción y Alcance

MONOMER (Multi-Objective Network Optimization for Multi-omics ER) es un framework diseñado para el descubrimiento de biomarcadores en cáncer utilizando algoritmos genéticos multiobjetivo.

🎯 ¿Qué problema resuelve?

Dado un conjunto de datos multi-ómicos (mRNA, miRNA, Metilación) con alta dimensionalidad (>20,000 features) y pocas muestras, MONOMER busca subconjuntos de características (firmas genéticas) que maximicen simultáneamente:

  1. Precisión Predictiva: Capacidad de clasificar subtipos o predecir supervivencia.
  2. Parsimonia (Leanness): Usar el menor número de genes posible.
  3. Diversidad/Peculiaridad: Encontrar mecanismos biológicos alternativos, no solo el más obvio.

⚠️ Alcance y Limitaciones

  • Enfoque: Feature Selection (Selección de Características) supervisada.
  • No resuelve: Preprocesamiento crudo (FASTQ -> Conteos), ni inferencia de redes regulatorias de novo.
  • Estado: Framework de investigación. Requiere conocimientos de Python y R para configuración avanzada.

📂 El Contrato de Interfaz (Filesystem)

La comunicación entre R y Python se realiza exclusivamente a través de archivos CSV planos ubicados en work/<nombre_dataset>/input/. Python no tiene conocimiento de la biología subyacente, solo ve matrices numéricas.

⚠️ Responsabilidad Estricta de R: El módulo Python InputData asume que los datos ya están limpios. Si un CSV contiene NaN, infinitos o cadenas de texto en las vistas, el proceso de Python fallará o producirá resultados basura. La imputación debe ocurrir en R.

Especificación de Archivos (Inputs)

Archivo Rol Formato Esperado (Pandas-ready)
*.csv (Vistas) Matrices de Características (X)
  • Filas: Muestras (Pacientes). Deben coincidir en orden y cantidad con el outcome.
  • Columnas: Features (Genes, CpG sites).
  • Índice: La primera columna debe ser el ID del paciente (string).
  • Valores: float. Preferiblemente normalizados (ej. Log2 TPM, Z-score).
outcome.csv Variable Objetivo (Y)
  • Índice: ID del paciente (debe hacer match exacto con las vistas).
  • Columna Target: Nombre de la clase (ej. Subtype_PAM50).
  • Supervivencia: Si es análisis de supervivencia, requiere dos columnas: time (float) y event (bool/int).

🛡️ Validaciones Automáticas en Python

Al instanciar la clase InputData, el sistema realiza las siguientes comprobaciones de integridad:

  • Consistencia de Muestras: Verifica que todas las vistas y el archivo de outcome tengan exactamente el mismo número de filas (pacientes).
  • Alineación (Implícita): Python asume que la fila i de mrna.csv corresponde al mismo paciente que la fila i de outcome.csv.
    Nota: Los scripts de carga en R (preprocess_utils.R) garantizan esto usando intersección de IDs antes de guardar.
Algoritmo

4. El Ciclo Evolutivo (GA Workflow)

El corazón de MONOMER es un algoritmo genético diseñado para evitar la convergencia prematura mediante mecanismos de diversidad social.

Fases del Ciclo

  1. Inicialización: Se crea una población de PeculiarIndividual. Se puede usar Feature Importance previa (ANOVA/Lasso) para sesgar la creación inicial (ver ga_strategy_bitlist.py).
  2. Evaluación Paralela:
    • El Master envía máscaras de bits a los Workers.
    • Los Workers entrenan modelos (SVM, RF) con esas características y devuelven el fitness.
  3. Cálculo Social: Antes de seleccionar, se calculan métricas secundarias:
    • Crowding Distance: Densidad en el espacio de objetivos.
    • Peculiarity: Singularidad en el espacio de genotipos (ver peculiarity_manager.py).
  4. Selección y Reproducción: Se usa torneo binario favoreciendo soluciones no dominadas y socialmente diversas.
Definiciones

5. Glosario Técnico

Referencia rápida de términos específicos utilizados en la arquitectura de MONOMER y sus diferencias con la literatura estándar.

Distinción Clave: Diversidad

MONOMER distingue dos tipos de diversidad para evitar óptimos locales:

  • Crowding Distance (Fenotipo): ¿Qué tan diferentes son los resultados (Accuracy/Leanness) de esta solución respecto a sus vecinos? (Estándar NSGA-II).
  • Peculiarity (Genotipo): ¿Qué tan diferentes son los genes seleccionados por esta solución respecto al promedio de la población? (Innovación de MONOMER).

Diccionario de Términos

Término Definición en el Contexto de MONOMER
Cross Hypervolume (CHV) Métrica de evaluación global. Generaliza el concepto de hipervolumen para validación cruzada, ponderando el volumen cubierto en el espacio de objetivos por la relación entre el rendimiento en entrenamiento y test (ver cross_hypervolume.py).
Hall of Fame (HoF) No es solo un registro histórico. Es la estructura dinámica que mantiene el Frente de Pareto actual (soluciones no dominadas) durante toda la ejecución. Es la fuente de verdad final del algoritmo.
Leanness Objetivo de maximización definido como $1 / (1 + N_{features})$. Busca la parsimonia: modelos con menos genes tienen mayor Leanness.
Social Space Métrica compuesta que combina la Crowding Distance y la Peculiarity. Se utiliza en la estrategia de ordenamiento secundaria para decidir qué individuos sobreviven cuando hay empate en dominancia.
View (Vista) Una modalidad de datos ómicos específica (ej. mRNA, miRNA, cnv). MONOMER puede fusionarlas (Early Integration) o tratarlas por separado.
PeculiarIndividual La unidad básica de evolución. A diferencia de un individuo estándar de algoritmos genéticos, este objeto transporta su contexto social y mantiene optimizaciones de memoria (Sparse Bitvectors) para manejar miles de genes.
Clone Index Mecanismo de penalización. Si dos individuos tienen el mismo genotipo, se les asigna un índice (0 para el original, 1, 2... para las copias) que degrada artificialmente su rango en el torneo de selección para forzar la diversidad.
Early Integration Estrategia de fusión de datos donde todas las vistas (matrices) se concatenan en una única gran matriz antes de entrar al algoritmo de aprendizaje.

8. Guía de Extensión y Lecciones Aprendidas

Análisis Post-Mortem basado en la implementación del algoritmo Artificial Bee Colony (ABC). Esta sección detalla los problemas de integración encontrados para evitar que futuros desarrolladores tropiecen con las mismas piedras al crear nuevos optimizadores (como PSO o ACO).

Contexto del Problema

Los errores documentados aquí no fueron fallos lógicos del algoritmo, sino errores de contrato con la arquitectura de MONOMER. El sistema asume ciertos comportamientos en los Individuos y el Evaluador que no siempre son obvios.

1. La Dualidad de los Individuos (Denso vs. Disperso)

AttributeError: ... object has no attribute 'active_features_mask'
  • Suposición Incorrecta: Asumir que todos los individuos heredan de una clase base densa estándar.
  • La Realidad: Para optimización con miles de genes, MONOMER usa PeculiarIndividualSparse (basado en conjuntos de índices). Las métricas de diversidad (como Jaccard) esperan una interfaz común para operar sobre máscaras.
Lección: Si tu algoritmo usa representaciones eficientes, asegúrate de que tu clase de Individuo exponga métodos de compatibilidad con Numpy: .sum(), .true_positions() y .active_features_mask().

2. La Interfaz de WorkerResult y Persistencia

AttributeError: 'NoneType' object has no attribute 'predict'
  • Suposición Incorrecta: Creer que evaluator.evaluate_batch asigna mágicamente el modelo entrenado al individuo.
  • La Realidad:
    • El evaluador devuelve un objeto WorkerResult.
    • Este objeto contiene una lista res.predictors() (uno por objetivo).
    • Muchos objetivos (ej. Leanness) devuelven None.
Lección: Es responsabilidad del Optimizador (en su bucle interno) extraer explícitamente el modelo válido del resultado y asignarlo: ind.set_predictors(res.predictors()). Si no se hace, el guardado final fallará.

3. Volatilidad del Hall of Fame (HoF)

Síntoma: Pérdida de modelos al guardar los mejores individuos al final de la ejecución.

  • Causa: Las librerías evolutivas (como DEAP) realizan copias profundas (deepcopy) al archivar individuos en el Hall of Fame. Esto a menudo rompe las referencias a objetos complejos no serializables o pesados como los modelos entrenados de Scikit-Learn.
Lección (Re-evaluación Obligatoria): Antes de retornar los resultados finales, extrae los supervivientes del HoF y fuerza una re-evaluación (evaluate_batch). Esto regenera modelos "frescos" en memoria listos para ser serializados correctamente.

4. La Interfaz de SortingStrategy

AttributeError: ... object has no attribute 'sort'
  • Suposición Incorrecta: Buscar un método estándar .sort().
  • La Realidad: El ordenamiento en MONOMER es complejo (NSGA-II/III, Crowding, Social Space). La interfaz es funcional y devuelve una nueva lista.
Firma Correcta: new_pop = strategy.apply_before_selection(pop, hp_manager)

✅ Checklist para Nuevos Algoritmos

Si vas a implementar pso_optimizer.py (Partículas) o aco_optimizer.py (Hormigas), verifica esto antes de ejecutar:

Verificación
🔲 Compatibilidad: ¿Tu Individuo responde a sum() y actúa como máscara booleana?
🔲 Captura: En el bucle de evaluación, ¿estás capturando res.predictors() y asignándolos con ind.set_predictors()?
🔲 Persistencia: ¿Estás re-evaluando los individuos del Hall of Fame justo antes del return final?
🔲 Estructuras: Si usas estadísticas manuales, ¿usas listas de listas para evitar errores en Pandas?

py/cross_validation/multi_objective/optimizer/lasso_mo.py

lasso_mo.py

Adaptación de Lasso (L1-regularized Logistic Regression) para generar un frente de Pareto.

Estrategia Multi-Objetivo

Lasso es inherentemente mono-objetivo. Para generar múltiples soluciones (trade-offs), este optimizador:

  1. Empieza con una regularización baja ($C=1.0$).
  2. Iterativamente reduce $C$ (aumenta la regularización) multiplicándolo por un shrink_factor (0.8).
  3. En cada paso, guarda la solución si tiene menos características que la anterior.

Esto produce una trayectoria de soluciones desde "muchos genes, alta precisión" hasta "pocos genes, menor precisión".

py/cross_validation/multi_objective/optimizer/rfe_mo_optimizer.py

rfe_mo_optimizer.py

Adaptación de Recursive Feature Elimination (RFE).

Estrategia

Similar a Lasso, RFE es mono-objetivo. Este optimizador:

  1. Entrena un modelo y calcula la importancia de características.
  2. Elimina las $N$ características menos importantes (Step).
  3. Guarda el subconjunto resultante como una solución candidata.
  4. Repite hasta quedarse sin características.

La colección de todos los subconjuntos intermedios forma el frente de Pareto aproximado.

  3. Calcula los valores en tres conjuntos de datos:
    • Train: Datos usados para entrenar.
    • Inner CV: Estimación interna durante la optimización.
    • Test: Rendimiento real en datos no vistos.
  4. Genera un gráfico PNG donde se puede visualizar el "gap de generalización" (diferencia entre Train y Test).

py/hall_of_fame/hall_of_fame.py | population_observer.py | hofers.py

Infraestructura Base del Hall of Fame

Conceptos Clave

  • PopulationObserver: Interfaz para objetos que reciben actualizaciones de la población en cada generación. Permite monitoreo pasivo.
  • HallOfFame (HoF): Almacén persistente de los mejores individuos encontrados durante toda la ejecución (no solo la última generación). Realiza copias profundas (deepcopy) para evitar modificaciones accidentales.
  • Hofers: Un contenedor inmutable (snapshot) que se devuelve al final de la ejecución. Es lo que reciben los evaluadores y "savers".
py/hall_of_fame/pareto_front.py

pareto_front.py

Implementación del Hall of Fame para Optimización Multi-Objetivo.

Lógica de Actualización

Cada vez que se intenta añadir un nuevo individuo:

  1. Si el nuevo individuo es dominado por alguno ya existente en el frente, se descarta.
  2. Si el nuevo individuo domina a algunos existentes, estos se eliminan y el nuevo entra.
  3. Si es no-dominado respecto a todos, coexiste con ellos.

Garantiza que al final solo tengamos el conjunto de soluciones óptimas de compromiso.
